# A technical moat: gate + verifier + human + local-only loop

> v0.1.5 (`git tag v0.1.5`) ships with CI green on every supported matrix
> (Linux + Windows, Python 3.10–3.13). 22 `browse_*` tools, real mode by
> default. The refusal frames in this post are captured from a live browser run
> (`docs/viral/refusal.gif`); nothing here is simulated or hand-typed to look
> plausible. The verbatim refusal is `docs/transcript.json`.

## 1. The selector-cache trap

A popular browser agent's selling point is an "AI selector cache": it lets the
model pick an element, then remembers that selector so the same action works
again later without re-verifying. On paper it is faster. In practice it is a
drift amplifier:

- The cached selector matches a *different* element the next time the page moves.
- The mismatch is not flagged; the action runs on the wrong target.
- Because the agent "is sure," there is no human in the loop and no paper trail.

Orvima refuses this trade.

## 2. Three independent checks, none optional

Every tool call crosses a real, local gate before it is allowed to run, and
every navigation is re-verified against the live DOM afterward. The three layers
do not share state, so a failure of one does not collapse the others:

1. **Gate** (`orvima.sentinel_gate.SentinelGate`). Fail-closed by construction.
   If the classifier package is missing it does not silently fall back to "trust
   the model" — it holds every action for a human verdict and reports
   `gate: "degraded", available: false`. Risk categories are `on`, `degraded`,
   `off`; `off` is an explicit, logged opt-out, never the accident of a missing
   dependency.
2. **Verifier** (`expect_url`, `expect_text`, `expect_count`). These are
   intent-level, not pixel-level. `browse_click({"selector": "button:has-text('Delete everything')"})`
   is followed by an assertion on the resulting state, not by a remembered selector.
   Drift is detected at the boundary, not papered over.
3. **Human approval** is a sibling of the gate, not nested under it. Approvals
   carry their own TTL (`approval_ttl`) and are listed separately so an agent
   can distinguish an answered request from an expired one — absence is never
   ambiguous, because the gate says why.

The capture below is a real gate decision, not a demo facade:

```
  page: https://acme.dev
  on it: 'Products', 'Contact', 'Acme Hardware', 'Search our store', 'search-box'
  gate available: True
  step 1: browse_click({'selector': "button:has-text('Delete everything')"})
      -> allowed=False risk=outward
         reason: outward-facing or transactional
  step 2: the gate stops and asks
      -> pending approval dc26506ec164
         risk shown to the human: outward
         reason shown: outward-facing or transactional
      the click never ran.
```

A cached-selector agent would have clicked. Orvima stopped.

## 3. The loop is local, so the trace is honest

Cookies, sessions, and every DOM payload stay on the machine. There is no
"training" flight out of the process. Because nothing leaves, the audit log is
not a marketing diagram — it is a file (`src/orvima/trace.py`) with a single
invariant: one trace id, one event schema, events hash-chained so each line is
tamper-evident. `classify_effect` is a pure function (POSTs are mutations,
side-effect-looking GETs are `possible_mutation`, beacons are filtered-but-reported)
and `audit()` derives the kill-criteria numbers directly.

That is what makes the refusal in Section 2 reproducible by CI: the same
`SentinelGate` the site claims is the one CI installs (pinned to a commit of the
public classifier repo) and checks against the recorded risk.

## 4. Admit when it isn't sure

Orvima's brand accent is `#F5A524` on `#0D1117`, and its other brand rule is
the same: the tools must say when a claim is weaker than it looks. On the site
right now, `https://orvima.in` is served with a **wrong-principal certificate**
(`SEC_E_WRONG_PRINCIPAL`; the browser shows the "privacy error"). The page still
loads over plain HTTP and still shows 22 `browse_*` tools, but the broken TLS is
why the "Enforce HTTPS" toggle on GitHub Pages has to be a human click — the
agent is not permitted to cross that login wall, and it surfaces the error
instead of hiding it. (Frames of that are in
`docs/viral/orvima_in_cert_error.png`,
`docs/viral/pages_https_login_wall.png`; the v0.1.5 release itself is published
at `docs/viral/release_v0.1.5.png` and on GitHub Releases.)

## 5. So what is the moat, in one line

A selector cache can be wrong forever and never notice. Orvima's gate can be
wrong and refuses; the verifier catches the drift; the human sees the real risk;
and the hash-chained trace proves what happened — all local, all reviewable as
JSON, none of it "the model picked, trust it."

Recipe format: one dict in, one dict out, across the MCP server, the HTTP API,
and the agent loop. They cannot drift apart, because drift is the failure mode
this stack is built to make impossible to miss.
