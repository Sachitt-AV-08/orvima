Tool Reference — all 22 browse_* tools

Every tool is dict-in, dict-out with verified on every action.

browse_navigate open-world

Open a URL. Waits for the page to be interactive and returns URL + title. Optional ``expect_url`` / ``expect_text`` state what the page should look like once it has loaded. If one is given and does not come true within ``expect_timeout_ms``, the call fails with the mismatch rather than reporting a successful navigation - which is how a redirect to a login page or the wrong account goes unnoticed. Omit them for today's behaviour. The check is the same on every backend, real browser or offline. A backend that cannot read the page it claims to have reached reports ``verified: false`` rather than ``verified: true``.

Why these hints: changes the current page and loads a URL the caller did not verify

browse_click destructive open-world

Click an element by CSS selector OR stable ref (e.g. 'e12' from snapshot). Prefer refs — they survive DOM churn. Returns ``verified: true`` if the click caused a navigation or DOM mutation; otherwise ``verified: false``. That check only asks whether *something* changed, which a click on the wrong element can pass. To judge the click against intent instead, state what you expected: - ``expect_url`` - a substring the resulting url must contain - ``expect_text`` - a substring the resulting page must show - ``expect_count`` - the exact number of matching elements afterwards, and ``expect_for`` a selector to count (default: the element you clicked) All optional and all polled for up to ``expect_timeout_ms``, since the result of a click is often asynchronous. If any expectation is unmet the call fails and names every mismatch, rather than reporting success.

Why these hints: a click can submit, pay, or delete; the most destructive common action

browse_hover read-only idempotent open-world

Hover an element by selector or ref.

Why these hints: moves the pointer, which can fire hover handlers but submits nothing

browse_select destructive open-world

Pick an option in a ``. ``paths`` are local file paths. Returns ``pageSaw`` - what the page's own FileList ended up holding - because attaching the wrong file silently is how a resume goes out with someone else's CV. Fails if a path does not exist or the target is not a file input. It will not guess, and it will not attach an empty selection.

Why these hints: hands files to an upload control, sending them off the machine

browse_open_tab open-world

Open a URL in a new tab and switch to it.

Why these hints: creates a tab and loads a URL; changes browser state

browse_list_tabs read-only idempotent

List open tabs with index, url and which one is active.

Why these hints: reads orvima's own tab list; touches no remote system

browse_switch_tab idempotent

Switch to another open tab by its list index.

Why these hints: changes which tab is active; a repeat is a no-op

browse_close_tab idempotent

Close a tab by index (never the last remaining one).

Why these hints: closes a tab, discarding its state; not repeatable once gone

MCP Prompts — prepared workflows

Invoke by name from any MCP client. Each returns a structured prompt template with placeholders you fill in.

orvima/verify-action

Verify an action actually did what you expected — Run a tool, then snapshot and extract the specific thing you expected to change. Returns a compact verdict. Use this instead of trusting ok: true — the whole point of Orvima is that it re-reads the DOM.

Arguments:

  • action_tool (required) — The browse_* tool to run (e.g. browse_click, browse_fill)
  • action_args (required) — Arguments for that tool (selector/ref/text etc)
  • expectation (required) — What you expect to see change (e.g. 'cart count becomes 1', 'modal closes')
  • selector_or_ref (required) — Selector or ref of the element to read after the action

orvima/extract-table

Extract a table from the current page as structured data — Snapshot the page, find the table by selector, then extract rows and cells into a JSON array. Handles pagination by defaulting to the first page — pass continue=true to fetch more.

Arguments:

  • selector (required) — CSS selector for the element (or its container)
  • continue (optional) — Whether to paginate (not implemented yet — reserved)

    • orvima/read-article

    Read the main article content from a news/blog page — Navigate to a URL, strip boilerplate (nav, ads, sidebars), and return the article text. Uses browse_extract on common article selectors with a fallback to the full body text.

    Arguments:

    • url (required) — The article URL to read

    orvima/compare-prices

    Compare prices on two product pages — Open two URLs, extract the price from each using a selector, and return a simple comparison. Useful for flight/hotel/shopping checks.

    Arguments:

    • url_a (required) — First product URL
    • url_b (required) — Second product URL
    • selector (required) — CSS selector for the price element on both pages

    orvima/submit-form

    Fill and submit a form with verification — Navigate to a page, fill fields by selector/ref, submit, then verify the result (success message, redirect, confirmation number). The gate will hold the submit if it looks destructive.

    Arguments:

    • url (required) — Page containing the form
    • fields (required) — Array of {selector, value} pairs to fill
    • submit_selector (required) — Selector for the submit button
    • expectation (required) — What success looks like (e.g. 'order number appears')

    orvima/wait-and-extract

    Wait for an element to appear, then extract its text — Polls for a selector (with browse_wait_for), then extracts text. Useful for dynamic content that loads after a click or navigation.

    Arguments:

    • selector (required) — Selector to wait for and then extract
    • timeout_ms (optional) — Maximum time to wait (default 10000)

    Architecture

    Three layers, one contract.

    MCP Server (stdio)

    Exposes 22 browse_* tools + 6 prompts over stdio. Any MCP client (Claude, Cursor, Copilot, your agent) gets hands on your browser.

    HTTP API (127.0.0.1:8301)

    REST + SSE for the local UI, programmatic control, and the phone approval page. Same contract as the MCP tools.

    Agent Loop

    Plans → acts → verifies. browse_snapshot after every step. If verified: false, the loop retries or escalates to the gate.

    Approval Gate (Sentinel)

    Classifies every tool call. Destructive actions wait for a human. The gate reads the page now, not when the approval was queued. Expired approvals disappear.
